Flujo de una Petición HTTP

Qué ocurre entre que un componente de listado llama a service.getAll(filtros) y que la tabla se repinta. En medio: buildHttpParams, el authInterceptor que adjunta el Bearer token y vigila la expiración, el backend en localhost:8080, y el desempaquetado de ApiResponseWrapper<T>. Desenlaces posibles

2xx — éxito

El componente hace response.data, this.provincias.set(...) y baja el flag cargando. Si usa ChangeDetectorRef en vez de signals, aquí va el markForCheck().

401 — no autenticado

El interceptor llama authService.logout() y navigateByUrl('/auth/session-expired'). El error se re-lanza; el error: del componente también se ejecuta.

403 — sin permiso

El interceptor redirige a /auth/access-denied. No hay logout: el token sigue siendo válido, falta autorización.

500 / 502 / 503 / 504 / 0

Redirige a /500 (AUTH.ROUTES.SERVER_ERROR). El status: 0 cubre el caso de backend caído / CORS / red.

Antes de la request: si el token existe pero tokenService.isExpired(token) es true (compara payload.exp * 1000 con Date.now()), el interceptor corta en seco: logout() + redirección a session-expired y devuelve throwError — la petición nunca sale. Las URLs que contienen un fragmento de AUTH.PUBLIC_ENDPOINTS (/login, /refresh-token…) se saltan todo esto y van sin cabecera.
paramsbuildHttpParams(filtros) descarta null/undefined/'' y trata activo como triestado: '1'→true, '0'→false, '2'→se omite (“Todos”).
wrapperApiResponseWrapper<T>: { message, data, success, fieldErrors }. Los listados tipan contra esto; las acciones puntuales a veces usan ApiResponse<T> (solo message/data) — es inconsistente entre servicios.
tokenTokenService lee de sessionStorage (no localStorage). decodePayload hace atob del segundo segmento del JWT.
verbosgetAll/get → GET · cambiarEstado → PATCH · borrarRegistro → DELETE · add → POST · update → PUT. Todos con Content-Type: application/json.
